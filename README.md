# Telegram Restaurant Booking Agent

Агент для бронирования столика через Telegram: сам начинает вежливый разговор на английском, обрабатывает ответы ресторана, уточняет неизвестные сведения и отправляет итоговое подтверждение после проверки условий.

Переписка с рестораном идёт **с пользовательского аккаунта через Telethon (MTProto)**. Отдельный бот на aiogram — панель управления для регистрации клиента, создания заявки, уведомлений и скачивания журнала. Bot API используется для панели, а не для отправки заявки ресторану. Готовый сервис бронирования не используется.

## Возможности

- Два отправителя: заранее подключённый аккаунт представителя сервиса или личный аккаунт клиента, подключённый через QR.
- Форма заявки: имя и фамилия, число гостей, дата, время, допустимый интервал и вручную введённый адресат.
- **«🙋 Если время занято — спросить меня»**: альтернативы за пределами первоначального времени передаются владельцу. Агент ждёт выбора, не соглашаясь и не завершая диалог самостоятельно. Владелец нажимает «Ответить менеджеру», выбирает предложенное время или «Нет». Новое время становится разрешённым только после явного выбора; ресторан затем должен подтвердить бронь. Ожидание сохраняется после перезапуска. Строгое время и автоматическое согласование внутри диапазона остаются отдельными режимами.
- Кнопки **«✍️ Написать текстом»** и **«🎙 Отправить голосовое»**: выбранный формат применяется к первому сообщению и дальнейшим ответам этого диалога.
- Groq получает структурированную заявку и историю конкретной беседы; неизвестные личные сведения запрашиваются у клиента, неоднозначные условия — у ресторана.
- Проверка распознанных альтернатив по допустимому времени, включая британское `half five or six`. Для строгих 17:00 предложения 17:30 и 18:00 отклоняются.
- Название ресторана запоминается из беседы. Если после подтверждения остальных условий оно неизвестно, агент тактично уточняет его в конце.
- Сохранение состояния, маршрутов и журнала с отдельной строкой на каждое сообщение.

## Установка

Требуется Python 3.11+. Последние автоматические проверки выполнялись на Windows с Python 3.14. Используемое хранилище сессий — Windows Credential Manager через `keyring`.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev,voice]"
Copy-Item .env.example .env
```

Заполните локальный `.env`:

- `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` — параметры собственного приложения с my.telegram.org.
- `CONTROL_BOT_TOKEN` — токен отдельного бота панели управления из BotFather.
- `LLM_PROVIDER=groq`, `GROQ_API_KEY` — провайдер и ключ разговорной модели; модель задаётся `GROQ_MODEL`, в примере — `openai/gpt-oss-20b`.
- `VOICE_MODE=auto` — распознавание голосовых и голосовой ответ на них, если формат не выбран кнопкой явно.

Ключи вводятся только локально. `.env.example` не содержит секретов. Бесплатные квоты и доступность моделей зависят от аккаунта провайдера; приложение не подключает платный тариф.

Для режима представителя подключите его аккаунт в консоли:

```powershell
python -m booking_agent.connect_representative
```

Авторизация выполняется локально, сессия сохраняется через `keyring`. Личный аккаунт подключается через QR в панели. Пароль 2FA и код входа не следует отправлять в чат: если QR-вход требует дополнительной авторизации, текущий интерфейс сообщает об ограничении и не запрашивает пароль.

## Запуск и бронирование

```powershell
python -m booking_agent.commercial_control_bot
```

1. Откройте управляющего бота, отправьте `/start` и выберите отправителя через **«🔄 Сменить режим»**.
2. Нажмите **«📝 Новое бронирование»**, заполните заявку и вручную введите адресата.
3. Проверьте детали и фактический аккаунт отправителя.
4. Нажмите кнопку отправки текстом или голосовым. **Нажатие сразу отправляет заявку**; до этого внешних сообщений нет.
5. Следите за уведомлениями. При неизвестных личных сведениях нажмите **«✍️ Ответить менеджеру»** и введите ответ по-английски. Он передаётся без перевода; перед ним может добавляться уже выбранное допустимое время.
6. После завершения скачайте журнал и сохраните скриншоты непосредственно Telegram-переписки.

В текущей панели разрешены только `@project_sync_bot` (тест) и `@vlad_dev_7` (адресат задания). Автоматического выбора получателя нет. Для исходного задания укажите **двух гостей, сегодняшнюю дату по Лондону и ровно 17:00, без диапазона**. Истёкшее допустимое окно не переносится автоматически на другую дату.

На один аккаунт отправителя допускается один активный диалог в процессе панели. Блокировка по токену предотвращает запуск второго экземпляра панели. После перезапуска взаимодействие клиента с панелью может восстановить безопасно ожидающий диалог без повторной отправки первого сообщения. Состояния с неопределённой доставкой требуют ручной проверки. Все беседы не восстанавливаются фоново сразу при старте.

## Проверка

```powershell
python -m pytest -q
```

Последний полный прогон: **132 теста прошли**. Автотесты имитируют Telegram и LLM, не расходуют квоту Groq и не пишут менеджеру. Проверяются подтверждение, альтернативы времени, дополнительные вопросы, журнал, доставка, восстановление и голосовой транспорт.

**«🧪 Проверить диалог локально»** запускает репетицию с имитированными сообщениями менеджера. При `LLM_PROVIDER=groq` ответы формирует настоящий Groq: он получает тестовую заявку и историю. `LLM_PROVIDER=offline` — ограниченный детерминированный режим без LLM-ключа.

Для живого теста используйте тестового собеседника. Тест со вторым личным аккаунтом требует соответствующей настройки разрешённых адресатов.

## Голосовые сообщения

Распознавание: Groq Whisper `whisper-large-v3`. Английская озвучка: `canopylabs/orpheus-v1-english`, голос `troy`. Используется существующий ключ Groq; для Orpheus может потребоваться отдельно принять условия модели в организации владельца ключа. `imageio-ffmpeg` предоставляет FFmpeg для преобразования WAV в OGG Opus, который Telethon отправляет как голосовое сообщение.

Значения `VOICE_MODE` для диалогов без явно выбранного формата:

- `off` — распознавание отключено, в ответ на голосовое запрашивается текст.
- `auto` — голосовой ответ на голосовое, текстовый на текст.
- `always` — все исходящие ответы, включая первый, озвучиваются.

Кнопка отправки голосовым включает озвучивание для заявки независимо от значения по умолчанию. Кнопка отправки текстом сохраняет исходящие ответы текстовыми; распознавание входящих голосовых в этом случае зависит от настройки окружения. Выбор сохраняется при восстановлении диалога.

Проверка синтеза и распознавания без Telegram:

```powershell
python -m booking_agent.voice_check
```

Команда создаёт вымышленную реплику, преобразует её в OGG Opus, распознаёт обратно и сохраняет `data/voice-check.ogg`. Для проверки в Telegram отправьте голосовое от тестового собеседника в активном диалоге.

Входящее аудио ограничено **120 секундами и 8 МиБ** и отправляется в Groq для распознавания. Ненадёжная или неудачная расшифровка приводит к просьбе написать текстом. Ошибка синтеза приводит к текстовому ответу до попытки отправки. Если сама отправка в Telegram завершилась с неопределённым результатом, диалог останавливается без повторной отправки текстовой копии. Панель показывает расшифровку и текст озвученного ответа; журнал отмечает формат. Сырые входящие аудиофайлы не сохраняются, временные файлы преобразования удаляются. Голос реализован в коммерческой панели, а не в старом консольном интерфейсе.

## Журнал и хранение данных

Живые диалоги: `data/live-dialogues/<client-id>/<booking-id>/`. Репетиции: `data/local-dialogues/<client-id>/<booking-id>/`.

- `state.json` — заявка, состояние и история.
- `transport.json` — фаза транспорта, адресат, отправитель и формат.
- `decisions.jsonl` — исходные диагностические события.
- `messages.jsonl` — одна запись на сообщение с кратким пониманием, решением, форматом и доставкой.
- `decision-log.txt` — читаемый экспорт, одна физическая строка на сообщение.

**«📄 Скачать журнал»** экспортирует последний доступный диалог клиента. Для конкретного прогона:

```powershell
python -m booking_agent.export_log "data/live-dialogues/CLIENT_ID/BOOKING_ID"
```

`sent` означает, что Telegram вернул ID сообщения, а не что адресат его прочитал. `unknown` — доставка после ошибки не установлена, автоматического повтора нет. Репетиции помечаются `simulated`; их журнал нельзя выдавать за реальную переписку. Экспорты могут содержать личные сведения — перед передачей проверьте их состав.

SQLite хранит клиентов, настройки и маршруты; JSON — состояние и журналы. Эти файлы не шифруются приложением. Сессии нового подключения хранятся отдельно через Windows Credential Manager, а не в SQLite или открытом файле сессии. Это не защищает от программы или человека с доступом к тому же Windows-профилю. `.env`, `data/`, `*.session` и виртуальное окружение исключены из Git.

## Архитектура и ограничения

`commercial_control_bot.py` — интерфейс; `live_dialogue.py` — Telegram-транспорт; `engine.py` и `llm_policy.py` — решения и проверки; `providers.py` — адаптеры моделей; `voice.py` — речь; `database.py` — SQLite; `store.py` — состояние и журнал; `secure_session.py` — сессии. Сохранены ранние `main.py` и `control_bot.py`; основной сценарий — `commercial_control_bot.py`.

Рабочий разговорный путь проверен с Groq. В коде также есть адаптер Gemini, но это не означает равнозначного покрытия текущего сценария. Полный контекст заявки и переписки передаётся выбранному LLM-провайдеру.

Модель предлагает действие, но окончательное подтверждение проверяет код: число гостей, дата, допустимое время и известное название ресторана должны опираться на переписку. Подтверждённые условия могут сохраняться до отдельного ответа с недостающим названием. Неоднозначность требует уточнения; ошибки API останавливают диалог для проверки. Эти меры не гарантируют безошибочного понимания любого текста или аудио: необычные имена, шум, акценты, даты и числа могут распознаваться неверно. Текущая версия — локальный прототип для задания; для многопользовательского сервиса нужны дополнительная защита данных, мониторинг и доработка авторизации.
